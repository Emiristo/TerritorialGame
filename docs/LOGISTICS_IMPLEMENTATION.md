# Logistics foundation

> Статус: актуальный технический документ о состоянии реализации логистики.
>
> Общие правила логистики находятся в `docs/GAME_RULES.md`.

## 1. Что уже реализовано

- каждое здание связано с одним логистическим флагом;
- флаги хранятся отдельно от зданий и ссылаются на своё здание;
- флаг имеет позицию на карте и список подключённых дорог;
- дороги являются физическими путями по клеткам карты между двумя флагами;
- логистическая сеть представлена графом флагов;
- маршруты между флагами ищутся по дорожной сети;
- сеть умеет перестраиваться после изменения состава дорог/флагов;
- удаление здания через `destroyBuilding` удаляет его флаг и связанные дороги;
- после перестроения сети недействительные маршруты не возвращаются;
- реализовано планирование логистических задач с выбором ближайшего доступного потребителя по дорожной сети;
- приоритет планирования: прямой потребитель производственного ресурса → склад, если прямого потребителя нет;
- для потребляющих зданий реализована ограниченная входная ёмкость: 4 ячейки, только для ресурсов из их рецепта;
- реализованы базовые операции резервирования, погрузки/доставки и конечной передачи груза работнику здания;
- реализована пропускная способность дороги уровнями 1–3 и порогами 200/400 успешно перевезённых единиц;
- складская модель разделяет дежурного носильщика склада и дорожного носильщика;
- отдельные тесты покрывают ключевые правила планирования и ёмкости.

## 2. Сквозная транспортная заявка

Одна транспортная заявка описывает **весь путь конкретного груза от исходного хранилища/производства до конечного получателя**. Заявка не создаётся заново для каждого участка дороги.

Сквозная заявка должна сохраняться на протяжении всей цепочки:

`источник → флаг источника → дорожная сеть → флаг получателя → конечное хранилище/вход здания`

При этом заявка и перевозчик — разные сущности:

- **заявка** отвечает за логистическую потребность и отслеживает продвижение груза по всему маршруту;
- **груз** физически находится в одном месте в каждый конкретный момент;
- **перевозчик** отвечает только за текущий участок физического перемещения;
- **флаг** является точкой передачи груза между независимыми участниками логистики.

### 2.1. Начало складской доставки

Груз **изначально находится в инвентаре склада**. Он не появляется сразу на флаге.

Правильная последовательность:

`складской инвентарь → носильщик склада → флаг склада`

После того как носильщик склада положил груз на флаг склада, его работа по этому грузу закончена. Он освобождается и может немедленно взять следующий груз, даже если сквозная транспортная заявка первого груза ещё не завершена.

### 2.2. Передача между дорожными перевозчиками

Каждый дорожный перевозчик выполняет только один текущий участок маршрута:

`флаг A → дорожный перевозчик → флаг B`

После доставки груза на флаг B:

1. груз остаётся на флаге B;
2. текущий перевозчик освобождается;
3. перевозчик может получить следующую транспортную задачу;
4. сквозная заявка продолжает существовать;
5. следующий участок маршрута может быть выполнен другим свободным перевозчиком.

Перевозчик **не должен удерживать груз до конечного получателя** и **не должен ждать закрытия сквозной заявки**.

Пример многосегментного маршрута:

`склад → флаг A → флаг B → флаг C → флаг здания`

Один груз последовательно передаётся между перевозчиками:

`перевозчик №1: A → B`

`перевозчик №2: B → C`

`перевозчик №3: C → флаг здания`

После каждой передачи предыдущий перевозчик свободен.

### 2.3. Состояние сквозной заявки

Состояние заявки описывает **состояние всей логистической операции**, а не жизненный цикл конкретного перевозчика.

Упрощённая модель:

`READY → IN_TRANSIT → READY → IN_TRANSIT → ... → AT_DESTINATION → DELIVERED`

Где:

- `READY` — заявка ожидает выполнения следующего участка маршрута;
- `IN_TRANSIT` — груз в данный момент перемещается на текущем участке;
- повторный переход `IN_TRANSIT → READY` означает прибытие на промежуточный флаг и готовность следующего участка;
- `AT_DESTINATION` — груз достиг конечного флага, но ещё не передан конечному получателю;
- `DELIVERED` — конечный получатель фактически получил груз.

**Прибытие на промежуточный флаг не закрывает заявку.**

**Освобождение перевозчика не закрывает заявку.**

**Заявка закрывается только после фактической передачи груза конечному получателю.**

### 2.4. Независимость перевозчиков

Сквозная заявка не должна создавать блокировку вида:

`перевозчик №1 занят заявкой → ждёт перевозчика №2 → не может взять следующий груз`.

Правильная модель:

`заявка №123`

`груз №123`

`перевозчик №1 → участок 1 → свободен`

`перевозчик №2 → участок 2 → свободен`

`перевозчик №3 → участок 3 → свободен`

Все перевозчики работают независимо, а состояние одной сквозной заявки используется для определения того, какой участок должен выполняться следующим.

Это позволяет логистической сети работать непрерывно и обеспечивает параллельную обработку множества грузов.

## 3. Дороги

Текущая дорожная модель предусматривает:

- путь состоит из клеток карты;
- дорога соединяет два логистических флага;
- маршрут между флагами строится по графу дорог;
- для выбора маршрута используется дорожная сеть, а не евклидово расстояние;
- изменение сети требует перестроения графа;
- уровень дороги определяет число одновременно выполняемых независимых транспортных задач на её участке;
- максимум — уровень 3.

Правила проверки геометрии дороги и ограничения пересечений являются частью кода и соответствующих автоматических тестов.

## 4. Логистическое планирование

При появлении ресурса на флаге производителя планировщик действует по приоритету:

1. найти ближайшее по дорожной сети доступное производственное здание, которому нужен именно этот ресурс и у которого есть свободная входная ёмкость;
2. если потребитель найден — направить ресурс непосредственно ему, минуя склад;
3. если потребитель не найден — направить ресурс на ближайший доступный склад.

Для потребляющего здания действует отдельная входная ёмкость из **4 ячеек**. Эти ячейки принимают только ресурсы, перечисленные во входном рецепте здания.

## 5. Физическая модель склада

Для складской доставки используется цепочка:

`складской инвентарь → носильщик склада → флаг склада → дорожный носильщик → дороги → конечный флаг → носильщик здания/склада → конечное хранение`

Важно: **груз сначала находится в инвентаре склада**. Носильщик склада физически переносит его на флаг склада. Только после этого дорожная логистика получает возможность забрать груз с флага.

Достижение флага склада или конечного флага не считается полной доставкой. На промежуточном флаге груз ожидает следующего перевозчика. На конечном флаге груз ожидает конечного носильщика.

## 6. Связь с производством и строительством

Производство должно помещать готовую продукцию в выходную ячейку производящего здания. Работник здания переносит готовый продукт из выходной ячейки на флаг здания, после чего логистика создаёт/продолжает транспортировку к следующему потребителю.

Приоритет вывоза готовой продукции:

1. запрос другого производственного здания на этот ресурс;
2. склад как fallback, если подходящего производственного потребителя нет.

Строительство использует ту же физическую идею флагов: строительный материал должен прибыть на флаг строительной площадки и **остаться там до забора строителем**. Доставка на флаг не равна использованию материала.

### 6.1. Положение строительного флага

Каждое здание получает ровно один строительный/логистический флаг непосредственно при размещении.

Флаг является **межклеточным узлом** и располагается по фиксированному правилу:

- всегда на **южной стороне** здания;
- по горизонтали — в узле **между 1-й и 2-й клетками здания**, если считать клетки с запада на восток;
- для здания с шириной 2 клетки это даёт положение строго по центру;
- для ширины 3, 4 и 5 клеток флаг находится немного левее геометрического центра;
- координаты флага вычисляются как `x = origin.x + 1`, `y = origin.y + height`.

Это правило является инвариантом размещения здания. Логистика и дороги используют уже созданный флаг и не должны самостоятельно пересчитывать его положение.

## 7. Принцип разработки

Логистика не должна подменять физическую модель упрощённым мгновенным переносом ресурсов между зданиями. Сначала фиксируется правило, затем реализуется соответствующий физический этап, затем добавляется автоматический тест, подтверждающий это правило.

При разработке транспортной системы отдельно проверяются:

- корректность сквозной заявки;
- физическое местоположение груза;
- передача груза между флагами;
- освобождение перевозчика после каждого участка;
- возможность перевозчика сразу принять следующую задачу;
- продолжение одной и той же заявки после промежуточных передач;
- закрытие заявки только после фактической доставки конечному получателю.
