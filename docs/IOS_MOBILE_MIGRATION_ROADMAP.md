# TerritorialGame — дорожная карта перехода на iOS

> Статус: проектный документ.
> Ветка разработки: `scaffold`.
> Цель: превратить существующую браузерную версию TerritorialGame в мобильное приложение для iPhone и iPad без переписывания игрового движка.

## 1. Исходная точка

На момент создания документа:

- игровой движок реализован на JavaScript;
- интерфейс работает через Vite;
- карта игры — 100×100 клеток;
- игровые механики покрываются автоматическими тестами;
- GitHub Actions выполняет игровые тесты и браузерную сборку;
- последний проверенный workflow успешно выполнил `Run game tests` и `Build browser game`;
- разработка ведётся на Windows 11 в IntelliJ IDEA;
- основное тестовое устройство — iPhone;
- Mac/Xcode у разработчика отсутствует.

Главный принцип перехода: **мобильная версия не должна становиться новой реализацией игры**. Мы сохраняем существующий игровой движок и добавляем мобильный слой взаимодействия и нативную оболочку.

# 3. Выбранная технология

## 3.1. Capacitor

Основной кандидат для мобильной оболочки — **Capacitor**.

Причина выбора: существующая игра уже является JavaScript/Vite-приложением. Capacitor позволяет сохранить web/game core и добавить нативный iOS-контейнер.

Не выбираем на текущем этапе:

- полный rewrite на Swift/SpriteKit;
- React Native rewrite;
- отдельный игровой движок;
- две независимые реализации игровой логики.

Такой rewrite увеличит объём работы и создаст риск расхождения механик между версиями.

# 4. Главный принцип разработки

## Game Core ≠ UI ≠ Platform

Нужно постепенно разделить проект на три уровня:

```text
Game Core
   ↓
Platform-independent logic

UI
   ↓
Browser + Touch interface

Platform
   ↓
Web / iOS / native APIs
```

Игровая логика не должна зависеть от `window`, DOM, конкретного размера экрана или mouse events.

Это позволит одновременно поддерживать:

- браузерную версию;
- iPhone;
- iPad;
- будущие платформенные функции.

# 5. Этап 0 — заморозка baseline

Перед мобильной разработкой фиксируется состояние игры.

### Проверки

- все существующие тесты проходят;
- browser build проходит;
- CI зелёный;
- игровая механика не меняется в мобильном коммите.

### Правило

Если мобильная задача ломает игровой тест, сначала выясняем, почему изменился Game Core. Не исправляем тест только ради зелёного CI.

Тесты проверяют механику, а не наоборот.

---

# 6. Этап 1 — подготовка web-версии к мобильному запуску

До появления нативного iOS-проекта нужно сделать web-версию пригодной для touch.

## 6.1. Viewport

Проверить:

- отсутствие горизонтального overflow;
- корректный viewport;
- масштабирование интерфейса;
- работу на узком экране;
- работу на высоком экране;
- landscape/portrait.

## 6.2. Safe Area

Интерфейс не должен попадать под:

- Dynamic Island;
- статус-бар;
- Home Indicator;
- системные края экрана.

Использовать CSS safe-area inset там, где это необходимо.

## 6.3. Touch input

Базовая модель:

| Действие | Управление |
|---|---|
| Выбор клетки | tap |
| Выбор здания | tap |
| Перемещение карты | drag одним пальцем |
| Масштабирование | pinch |
| Контекстное действие | long press |
| Центрирование/быстрое действие | при необходимости double tap |

Конкретные действия double tap не фиксировать заранее, пока они не понадобятся игре.

---

# 7. Этап 2 — мобильная карта

Карта — один из главных технических рисков.

Текущий размер — 100×100 = 10 000 клеток.

Нельзя строить архитектуру, предполагающую бесконечное увеличение DOM-узлов при дальнейшем росте карты.

## Требования

- pan;
- pinch zoom;
- корректное преобразование координат пальца в координаты карты;
- выбор клетки после zoom/pan;
- сохранение точности координат;
- отсутствие случайных кликов во время drag;
- плавная работа на iPhone.

### Отдельно проверить

```text
finger down
→ drag
→ map moves
→ finger up
```

не должно превращаться в:

```text
drag
→ случайный tile click
```

---

# 8. Этап 3 — мобильный UI

Текущий desktop-oriented интерфейс нельзя просто уменьшить.

Нужен отдельный responsive layout.

## iPhone

Приоритет:

1. карта;
2. выбранный объект;
3. основные действия;
4. строительство;
5. ресурсы;
6. логистика/статус;
7. второстепенная информация.

Панели должны открываться как компактные mobile sheets/panels, а не постоянно занимать большую часть экрана.

## iPad

Можно использовать более широкий layout:

```text
┌──────────┬──────────────────────┬──────────┐
│ player   │                      │ actions  │
│ / status │        MAP           │ / build  │
│          │                      │ / object │
└──────────┴──────────────────────┴──────────┘
```

Конкретный layout фиксируется после первого iPhone-прототипа.

# 10. Этап 5 — iOS-specific слой

После первого запуска внутри shell добавляем только действительно необходимые платформенные функции.

Потенциальные функции:

- haptic feedback;
- системные настройки ориентации;
- сохранение локального состояния;
- safe-area handling;
- управление статусом приложения;
- звук;
- уведомления — только если они понадобятся игре;
- Game Center — отдельный будущий этап.

Не добавлять native API заранее без игровой необходимости.

---

# 11. Сохранение игры

До полноценного iOS-релиза необходимо определить persistence layer.

Минимальная цель:

```text
Game State
    ↓
Save
    ↓
Local persistent storage
    ↓
App restart
    ↓
Load
```

Важно разделить:

- временное состояние текущего кадра/тика;
- сохраняемое состояние игры;
- настройки пользователя.

Не следует сохранять DOM как источник состояния. Источником истины должен оставаться Game State.

---

# 12. Жизненный цикл iOS-приложения

Мобильное приложение может:

- уйти в background;
- быть приостановлено;
- вернуться foreground;
- быть выгружено системой.

Поэтому необходимо проверить:

1. что происходит с игровым временем при background;
2. сохраняется ли состояние;
3. не создаются ли дублирующиеся timers;
4. не остаются ли старые event listeners;
5. корректно ли продолжается игра после возврата.

Игровое время не должно случайно ускоряться из-за повторного запуска таймера.

# 13. Производительность

Проверять производительность на реальном iPhone, а не только в desktop browser.

Контролируем:

- FPS/rendering;
- количество DOM-элементов;
- частоту перерисовки карты;
- количество игровых тиков;
- расчёт маршрутов;
- логистику;
- обработку touch events;
- потребление памяти.

Особое внимание:

```text
10 000 tiles
+ workers
+ roads
+ buildings
+ logistics
+ animation
```

не должны приводить к постоянной полной перерисовке всей карты без необходимости.

---

# 14. Офлайн-режим

Поскольку игра потенциально является локальной стратегией, базовая архитектура должна позволять запуск без постоянного интернет-соединения.

На первом этапе достаточно обеспечить:

- bundled game assets;
- локальный Game Core;
- локальное сохранение.

Сетевые функции, аккаунты и синхронизация — отдельный этап и не входят в первый iOS-прототип.

---

# 15. Сборка без собственного Mac

Разработка остаётся на Windows.

Проблема: полноценная нативная сборка iOS требует Apple toolchain/Xcode на macOS.

Поэтому предполагаемый pipeline:

```text
Windows / IntelliJ IDEA
        ↓
GitHub
        ↓
macOS runner / облачная сборка
        ↓
iOS build
        ↓
подпись Apple
        ↓
iPhone
```

На первом этапе нужно определить конкретный способ получения подписанной тестовой сборки.

Варианты следует оценивать отдельно:

- GitHub Actions на macOS;
- облачный Mac;
- другой CI/CD с macOS;
- временный доступ к физическому Mac.

Не покупать оборудование до проверки реальной необходимости.

---

# 16. Apple signing и установка на iPhone

Для реального тестирования нативного приложения потребуется Apple Developer infrastructure и корректная подпись приложения.

Нужно будет отдельно настроить:

- Apple ID;
- bundle identifier;
- signing certificate;
- provisioning;
- device registration, если выбран соответствующий способ распространения;
- TestFlight или другой допустимый способ установки тестовой сборки.

Эти данные не должны попадать в GitHub repository.

Секреты CI хранятся только в GitHub Secrets/соответствующем защищённом хранилище.

---

# 17. CI/CD после появления iOS

Pipeline должен стать двухуровневым.

```text
                 commit
                    │
          ┌─────────┴─────────┐
          │                   │
     Game validation       iOS pipeline
          │                   │
     Vitest + Vite       Capacitor + Xcode
          │                   │
          └─────────┬─────────┘
                    │
                 release
```

## Game validation

Каждый commit обязан проверять:

- игровые тесты;
- browser build.

## iOS pipeline

После появления рабочего iOS проекта:

- собрать iOS target;
- проверить проект;
- при настроенной подписи подготовить тестовую сборку;
- публиковать её только после прохождения Game Core tests.

# 18. Ручной QA на iPhone

Пользователь становится частью тестового контура.

Каждая тестовая версия проверяется минимум по следующим категориям:

### Запуск

- приложение открывается;
- нет белого/чёрного экрана;
- состояние загружается.

### Карта

- tap;
- drag;
- pinch;
- zoom;
- выбор клетки;
- выбор здания;
- строительство дороги;
- работа интерфейса после масштабирования.

### Игра

- workers;
- production;
- logistics;
- roads;
- flags;
- territory;
- transport requests;
- production input slots.

### Стабильность

- pause/background;
- возврат в приложение;
- блокировка/разблокировка экрана;
- длительная игра;
- сохранение/загрузка.

# 19. Правило изменения механики

Переход на iOS не является поводом менять игровую механику.

Если на iPhone обнаруживается механическая ошибка:

```text
iPhone обнаружил проблему
        ↓
воспроизводим в Game Core
        ↓
создаём/исправляем тест
        ↓
исправляем механику
        ↓
CI
        ↓
iOS build
        ↓
повторный тест на iPhone
```

Если проблема только в управлении:

```text
iPhone
 ↓
Input/UI layer
 ↓
исправление touch behavior
```

Game Core при этом не изменяется.

# 24. Стратегическая цель

Мобильный переход должен привести не к отдельной «iOS-игре», а к единому проекту:

```text
                  TERRITORIAL GAME
                         │
                  ┌──────┴──────┐
                  │  GAME CORE  │
                  └──────┬──────┘
                         │
          ┌──────────────┼──────────────┐
          │              │              │
       Browser         iPhone          iPad
          │              │              │
        Mouse          Touch          Touch
        Keyboard       Gestures       Gestures
```

**Один Game Core → несколько интерфейсов → одна система тестирования механик.**

Это является основным архитектурным принципом перехода на мобильное приложение.
